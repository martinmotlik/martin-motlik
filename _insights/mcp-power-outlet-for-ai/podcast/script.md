### Scene 2 · An outlet, not a brain  
*1168 characters · from original scene 2 (U02)*

**SARAH:** Okay, start from zero. What is it?

**MARTIN:** MCP is an open standard that lets AI apps connect to the software and data you already use. It doesn't make the AI smarter. It gives it a way to reach things outside itself. Your models, your analysis software, your project data.

**SARAH:** So, a plug.

**MARTIN:** Pretty much. Picture the temporary power spider box on a jobsite. It doesn't care if you plug in a saw, a grinder or a work light, because every tool has the same plug. Before MCP, connecting an AI to a program meant custom wiring for every single pair.

**SARAH:** And now?

**MARTIN:** Now software can expose its tools through an MCP server, and compatible AI apps can connect to it. You still need the right connection and permissions. Anthropic introduced the standard in late 2024.

**SARAH:** We pay for Copilot. So in that picture, Copilot is...

**MARTIN:** The host. The app you type into. On the other side, a small server sits next to Revit, or next to the tool that reads your IFC files, and tells the AI what it can do.

**SARAH:** Tells it how?

**MARTIN:** Each tool has a description and a structured definition of its inputs. The AI uses those to choose a tool and supply the information it needs. The application controls which tools are available.

### Scene 3 · Guessing vs. checking  
*1300 characters · from original scene 4 (U04, U05)*

**SARAH:** So back to the doors. What would have been different?

**MARTIN:** The AI would have a way to query the actual model. A tool can open the IFC file, find the doors and return their properties. We can check those results. The AI can still choose the wrong filter or misread an answer, so the connection alone doesn't make it reliable.

**SARAH:** So the AI is more of a coordinator.

**MARTIN:** Exactly. Like a good BIM coordinator, actually. It doesn't author the model. It knows where to look, and it brings back the answer.

**SARAH:** But here's the thing. Copilot already reads our documents. Our BIM Execution Plan, our standards. Isn't that the same?

**MARTIN:** That's a different tool, and a good one. The AI searches documents and quotes them. It answers "what does the BIM Execution Plan say?"

**SARAH:** And MCP?

**MARTIN:** MCP can connect both kinds of tools. One searches your documents; another queries the model or runs a check. The useful difference is what the tool can do. Most serious workflows will use both.

**SARAH:** Give me something real. What would our team actually ask?

**MARTIN:** Find the doors on level two with a missing fire-rating property, and show me where they are. Or total the concrete quantities in the slabs, floor by floor, if the model contains reliable quantities. Those are questions the connected tools can answer.

**SARAH:** [laughs] And the doors would have been real doors.

### Scene 4 · "Have you actually tried it?"  
*1515 characters · from original scene 5 (U06, U07)*

**SARAH:** Can I be honest? Everything I read about this is a vendor demo. Have you actually tried it yourself?

**MARTIN:** I have. I'm building a model-review prototype, a web app for IFC models. It already checks models against information requirements and compares versions. So I wrote a small MCP server for it. Six tools, all read-only.

**SARAH:** Read-only meaning...

**MARTIN:** It can look, it can't touch. List elements, read their properties, run a check, compare two revisions, and hand me a link into the 3D viewer. That's it.

**SARAH:** But couldn't your model checker already do that without AI?

**MARTIN:** Yes. The checker already did the validation. What I added was a way to ask follow-up questions, connect the steps, and jump straight to the affected elements.

**SARAH:** And what did you test it on?

**MARTIN:** A real model. A residential building in Prague, a concept model with a garage, three apartment floors and an attic. Plus an IDS file with the project's data requirements.

**SARAH:** IDS. Remind me?

**MARTIN:** IDS is a buildingSMART standard for expressing selected information requirements in a machine-checkable form. You specify which elements need which data. A checker then tests the model against those rules. It checks the information, not whether the building is correctly designed.

**SARAH:** Oh. That's literally what our BIM coordinator does every Friday before a submittal. By hand.

**MARTIN:** Then she'll like this part. I asked: check the model against the IDS file. Which requirements fail, and which elements are affected? Two requirements failed. Thirteen elements, mostly doors without a fire rating.

### Scene 6 · One server, two AI apps  
*945 characters · from original scene 7 (U09)*

**SARAH:** Okay, but which AI did you use? We're a Copilot shop.

**MARTIN:** I tested the same server with ChatGPT and with Gemini in Google Antigravity. In that test, both reached the same findings. That doesn't mean every AI app connects in the same way. With Copilot, you need to check the specific product and your company's setup.

**SARAH:** Was building the server the hard part?

**MARTIN:** Writing the code wasn't the hard part.

**SARAH:** What was?

**MARTIN:** Three things. First, the tool descriptions. The AI picks tools by reading them, so they're really the user interface. They deserve the same care as button labels.

**SARAH:** [laughs] Copywriting. Finally something in my lane.

**MARTIN:** Honestly, yes. Second, summaries beat data dumps. Return counts and the top results, with details on request. Send an AI a whole model and you overload its working memory. The answers get worse.

**SARAH:** And third?

**MARTIN:** Units and IDs, always. Every number carries its unit, every element its ID. Ambiguity is exactly where the AI starts guessing again.

### Scene 7 · "Why give our data to big tech?"  
*1181 characters · from original scene 8 (U10)*

**SARAH:** Here's where I push back a bit. Why would we connect our projects to OpenAI or Google or Microsoft? Wouldn't it be safer to build our own chatbot?

**MARTIN:** Fair question. Let me separate two things: where the model lives, and where the answers go. A local server keeps the model file on your machine. Only what the tools return goes to the AI.

**SARAH:** Which can still be a lot.

**MARTIN:** It can. So check your provider's terms on data retention and training before you connect live projects. And some clients and contracts don't allow commercial AI services at all. Then you don't.

**SARAH:** Okay. And the chatbot idea?

**MARTIN:** Building your own chatbot doesn't mean building your own language model. You can use the same commercial models behind a custom interface. The question is whether that interface solves a real problem for your team. MCP lets you reuse the engineering tools either way.

**SARAH:** And my engineers already have Copilot open all day.

**MARTIN:** Then it makes sense to start with the interface they already use, if it supports the connection you need. A custom assistant may still be useful for a specific workflow.

**SARAH:** So it's not either-or.

**MARTIN:** No. Keep the engineering tools reusable, then choose the interface that works for your team.

### Scene 8 · The weekend GitHub server  
*1219 characters · from original scene 9 (U11)*

**SARAH:** Okay, confession number two. One of our younger engineers found a community Revit server on GitHub and hooked it up to ChatGPT over the weekend. On a live project.

**MARTIN:** Of course he did.

**SARAH:** Our IT guy is not amused.

**MARTIN:** Your IT guy has a point. I separate three kinds of access. First, reading: querying the model and pulling properties. That limits changes to the model, but the information can still be sensitive.

**SARAH:** And the second?

**MARTIN:** Checking: IDS checks, clash reports, comparisons between revisions. People need to review the findings because they inform decisions. Third is writing: changing parameters or moving and creating elements. That needs controlled permissions and a way to review and undo changes.

**SARAH:** And the GitHub server?

**MARTIN:** You need to inspect what that particular server can do and what access it has. Autodesk now offers separate read, write and experimental server options as technical previews. The capabilities and permissions matter more than the label.

**SARAH:** Anything else I should tell IT?

**MARTIN:** Model data can contain text that tries to steer the AI. Read-only limits changes to the model; it doesn't prevent misleading answers or data exposure. Start with a trusted server, restricted access and a test model your firm has approved.

### Scene 9 · Who's actually shipping this?  
*759 characters · from original scene 10 (U12)*

**SARAH:** Who is actually shipping this in our industry?

**MARTIN:** Autodesk has Revit servers in technical preview. Bluebeam connects Revu with Claude. Trimble has a SketchUp connector, and Dlubal provides access to its analysis applications. The capabilities, supported clients and licenses differ. But these are actual products you can evaluate.

**SARAH:** Do they all give the AI the same kind of access?

**MARTIN:** No. Some expose a few defined actions. Others let the AI write scripts against an API. The reach depends on what the server exposes and the permissions behind it.

**SARAH:** Which would you start with?

**MARTIN:** A small set of read-only tools for one task. Scripting can go further, but you need to review and test the code. I've linked the product details in the article, because those are changing quickly.

### Scene 10 · What do I tell my boss?  
*1256 characters · from original scene 11 (U13, U14)*

**SARAH:** Okay. That email from my boss. And our senior engineer asked me to ask you one thing: who's liable if the AI gets it wrong?

**MARTIN:** Using AI doesn't remove the engineer's responsibility to review the result. The AI doesn't stamp drawings. How liability is allocated is a separate question for the firm's contracts and legal advice.

**SARAH:** So we still need a review process. What else do I write back?

**MARTIN:** That it won't clean up your data. It automates a messy process just as faithfully as a clean one. If your parameters are inconsistent, you'll just find out faster. And that it isn't free. AI subscriptions, and sometimes API access or add-on licenses on the software side.

**SARAH:** And then?

**MARTIN:** Then a few questions for every vendor. Do you ship an MCP server, official or community? Is it read-only, and are read and write separated? Where does project data go? The full list is in the article.

**SARAH:** And how do we know if it's worth it?

**MARTIN:** Choose one recurring task and a test model your firm has approved. Compare your current workflow, including any checker you already use, with the AI-assisted version. Count the review time, missed issues and false alarms as well as the time saved. Repeat it on another revision before deciding.

**SARAH:** That's our Friday model check.

**MARTIN:** That's your Friday model check.
